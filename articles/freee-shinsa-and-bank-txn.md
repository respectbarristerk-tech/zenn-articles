## 答えが出た2つの問い

7月末にfreeeのサポートデスクへ問い合わせて、**「審査を受けないと判断できない**」と回答された2点です。

| | 問い | 該当した場合 |
|---|---|---|
| Q1 | 一部入金の残額表示は「**高度な消込機能**」に該当するか | プラン限定アプリとなり、個人は会計プレミアム契約者にしか提供できない |
| Q2 | 未入金の検知と督促は「**金融サービス**」に該当するか | 金融サービス申請フォームからの追加申請が必要 |

Q1に該当した場合、**ターゲット層がまるごと消えます**。個人事業主向けのツールなのに、上位プラン契約者しか使えなくなるからです。

結果は**どちらも該当せず**でした。「金融サービス等の該当はなく、通常アプリとしてアプリストアへの公開が可能」という回答でした。

### 効いたのは、権限を参照のみにしていたこと

2本目にこう書きました。

> 権限を「参照のみ」にした判断が二重に効いた

三重になりました。

プラン限定アプリの定義は「債権の消込を高度なレベルで**行う**機能を持つアプリ」です。本ツールは書き込み権限を持っていないので、**消込は技術的に不可能**です。そして権限設定は審査で確認されます。

つまり「消込を行いません」が**自己申告ではなく、システム上の事実として確認できる**状態でした。文章で説明する必要すらなかった、というのが正確なところです。

### 期間は13日でした

- 8月11日　公開申請を提出
- 8月13日　審査事前確認フォーム（全9ページ）を提出
- 8月24日　結果の連絡

申請フォームには「通常3週間〜4週間」とありました。**実際は13日でした**。もちろん時期や内容によるはずですが、目安として。

## デモは求められませんでした

2本目に「画面共有でのデモを求められる場合もある」と書いたので、こちらも結果を残しておきます。

**求められませんでした。**

私は身構えて、デモ動画の台本を10,000字ほど書き、画面キャプチャをPDFにまとめ、想定質疑まで用意していました。日程調整のメールを送ったところ、返ってきたのはこれでした。

> アプリストアの公開については、弊社側での対応のため、小川様の対応は不要の認識でございます。

**公開はfreee側の作業で、開発者は何もしなくてよい**とのことでした。日程だけ決めて終わりです。

事前確認フォームで画面キャプチャを9ページ分提出していたので、そこで確認が済んだのだと思います。準備が無駄だったとは思っていません（3本目のバグは、デモを撮ろうとして見つかりました）が、**構えすぎなくてよい**という情報として。

## 銀行明細取得申請フォームの中身

`GET /api/1/wallet_txns` をパブリックアプリから叩くには、別途この申請が必要です。審査の結果が出たあと、改めてこのフォームへの回答を求められました。

3ページ構成でした。

**1ページ目**

- メールアドレス
- 申請内容についての承諾（チェック1つ）
- **アプリID**
- **銀行明細の取得目的**（自由記述）
- 開発者の属性（法人 / 個人）

**2ページ目**（個人を選んだ場合）

- 氏名
- **提供終了およびシステムの廃棄後の情報消去の対策**（4択）
- **取得した銀行明細の他サービスへの転用・転送**（2択）

**3ページ目**

- 銀行明細データの取扱いに関する承諾（チェック1つ）

「アプリID」が必須なので、**先にパブリックアプリを作っておく必要があります**。実装が終わっていなくても申請できますが、アプリの登録だけは先です。

### 取得目的に書いたこと

一番大きい欄です。私はこう書きました（抜粋）。

```
【銀行明細を参照する理由】
freee会計の「未決済」は「入金がない」ことを意味しません。
実際にはご入金いただいていても、消込作業が済んでいなければ未決済のままとなります。
この状態で督促を送ると、すでにお支払いいただいた取引先に催促することになり、
利用者と取引先の関係を損ないます。

これを防ぐため、GET /api/1/wallet_txns を参照し、status が 1（消込待ち）の
入金明細の中に、未決済取引と金額が一致するものがないかを確認します。

【利用範囲の限定】
・参照（GET）のみを行い、作成・更新・削除は一切行いません
・entry_side = income（入金）の明細のみを参照します
・照合に使用するのは金額・日付・摘要のみです
・取得した明細はサーバーに保存せず、上記の判定にのみ使用し、
　外部への送信や第三者への提供は行いません
・金融サービス（融資、資金移動、決済、収納代行等）の提供は一切行いません
```

**「何に使うか」より「どこまでしかしないか」を厚く書きました**。銀行明細は事業者の重要な取引情報なので、審査側の関心は「何を取るか」より「取ったものをどう扱うか」にあるはずだと考えたからです。

## 一番迷った設問

2ページ目のこれです。

> アプリの提供終了およびシステムの廃棄後に情報漏洩を発生させないため、機器等に保存されている情報を消去する等の対策を実施していますか？

選択肢は4つでした。

1. 下記に加えて、記憶媒体の破壊に関して破棄業者または第三者機関の証明書を取得している（クラウドサービスの場合、第三者機関の証明書を取得していることを確認している）
2. データ消去に加えて記憶媒体の破壊（再利用・売却不可能な状態にする）を実施している
3. **データを消去するルールを定め、運用している**
4. データ消去等の対策は実施していない

私の状況はこうです。

- **2は構造的に該当しない。** RenderとSupabaseを使っていて、記憶媒体を自分で持っていない
- **1は言えない。** 両社ともSOC 2 Type IIを公表していますが、私はそれを確認して答えているわけではない
- **4ではないはず。** 削除機能は作ってある

消去法で3ですが、そこで手が止まりました。**「ルールを定め、運用している」と本当に言えるのか。**

### 実装と規約を読み直した

確認したのは3か所です。

| | 内容 |
|---|---|
| プライバシーポリシー8条 | 「設定画面からいつでも保存されている情報をすべて削除できます」 |
| 利用規約9条 | 同旨 |
| 実装 | `POST /api/delete_account` が `DELETE FROM users`、履歴とフラグは `ON DELETE CASCADE` で連鎖削除 |

**利用者が自分で消すルールは、定めて運用していました。**

ところが設問が聞いているのは「**提供終了およびシステムの廃棄後**」です。サービス側が終わるときの話です。

利用規約第7条を読み直しました。

```
運営者は、利用者への事前の通知なく、本サービスの内容を変更し、
または提供を中断・終了することができます。
提供を終了する場合は、可能な限り事前に本サービス上で告知します。
```

**「終了できる」としか書いていない**。終了したあとデータをどうするかが、どこにも定めてありませんでした。

### 規約を先に直してから答えた

選択肢3を選ぶなら、その「ルール」が審査担当者の読める場所になければ意味がありません。なので**先に規約とプライバシーポリシーに追記し、デプロイしてから**フォームに答えました。

利用規約 第7条に追加した1文です。

```
本サービスの提供を終了する場合、運営者は、終了後速やかに、
保存されているすべての利用者情報（freeeのアクセストークンおよび
リフレッシュトークン、事業所ID・事業所名、作成した督促文の記録、
設定情報、取引の状態）をデータベースから削除します。
削除後の復元はできません。
```

プライバシーポリシーにも、自社で記憶媒体を保有しないため外部サービス上のデータ消去により行う旨を添えました。

作業としては15分です。ただ、順番が逆だったら意味がありませんでした。

### なぜそこまでするか

フォームの1ページ目に、こう書かれています。

> 本フォームには正確な情報をご入力ください。申請内容に虚偽等があった場合、freeeAPIへのアクセス停止などの必要な措置を取らせていただく場合があります。

**盛った回答は、1件でも反例が出た瞬間に申請全体の信頼を崩します**。しかも選択肢の文言と実態のズレは、後の追加確認で必ず突かれます。

選択肢に合わせて自分を語るのではなく、**選択肢に合うように事実のほうを先に作る**。それができない項目は、正直に下の選択肢を選ぶ。今回は前者でした。

なお、もう1つの設問「取得した銀行明細を他のサービスに転用・転送していませんか？」は迷いませんでした。**照合に使うだけで保存も外部送信もしていない**ので、「していない」で確定です。ここも「保存しない」という設計判断がそのまま答えになりました。

## 公開後の変更は1〜2週間かかる

公開日程を決めるやりとりで、一番効いた情報がこれでした。

freeeのご担当者いわく、**公開後に掲載内容（説明文や画像）を更新するには、改めて更新申請が必要で、再度審査が入る**とのことです。**画像・文章の更新でおおむね1〜2週間**、直近は申請が立て込んでいて2週間かかる場合が増えている、と。

これは設計判断に直結します。

**コードは何度でも書き直せます**。GitHubにpushすれば数十秒でデプロイされる。ところが**掲載文は、一度出したら2週間動かせません**。価格を試して素早く直す、という進め方が取れない。

なので、掲載内容についてはこう決めました。

- **更新申請は1回にまとめる**。細かい直しのたびに2週間を使わない
- 直したい点が出そろうまで、リストに溜めておく
- 溜めるためには、**利用者の声が要る**

最後の点のために、公開前にやったことがあります。

## 公開前にやったこと：フィードバックの受け口を作った

これまで、ご意見の窓口はメールアドレス1つだけでした。

**不具合報告ならメールを書く人もいますが、「こうだったら良かった」程度の要望でわざわざメールを書く人は、ほぼいません**。掲載文の誤解や使いにくさは、そういう温度の声でしか出てきません。

そこでフォームを作り、ヘルプページとアプリの設定画面に導線を置きました。ログイン不要、匿名で送れます。

設問で1つだけ工夫したのが、これです。

> **そのとき、実際に困ったことはありましたか？**
> 「あったら便利」と「無くて実際に困った」を分けて考えたいため、具体的な出来事があればお書きください。特になければ空欄で構いません。

**願望は誰でも書けますが、出来事は経験した人しか書けません**。この欄が埋まっている回答だけが、優先度を上げる材料になります。空欄なら「あったらいいな」だと分かる。選別を回答者に押しつけずに、こちらで判別できる形にしたつもりです。

ちなみに、freeeの掲載変更が2週間かかるのに対し、**ヘルプページとアプリ画面はこちらでデプロイすればいつでも変えられます**。再審査が要るのはfreee側のフォーム項目だけです。この線引きを知っておくと、どこに何を書くかの判断が変わります。

### 使ってくれる方を探しています

これまでも書きましたが、**私は会社員で、自分の請求書がありません**。未払いに困った当事者ではないので、このツールが本当に役に立つのかを自分では確かめられません。

freee会計で掛売上（未決済取引）を登録している個人事業主・フリーランスの方で、試してもよいという方がいらっしゃればご連絡ください。

督促を実際に送っていただく必要はありません。**連携して画面を開き、何が表示されたかを教えていただくだけ**で、私が自分では確かめられないことがほぼ分かります。

- 権限は**参照のみ**です。freeeの帳簿に書き込むことはできません
- 取引先の情報は、**作成した督促文の記録を除いて**サーバーに保存していません（その記録も暗号化しています）
- 設定画面からいつでも連携解除とデータ削除ができます
