freee APIを使った督促ツールを作り、アプリストアの審査に出しています。

審査の事前確認フォームに提出するデモ画面を撮っていたら、**アプリがまったく動かないこと**に気づきました。しかも**エラーは1つも表示されていませんでした。**

原因は2つ重なっていました。

1. **`/api/1/companies` の先頭の事業所を保存していた**（真因）
2. **エラー時に自動リダイレクトしていたため、1が見えなかった**

1は、事業所が1つしかない環境では**絶対に再現しません。**同じ踏み方をする人がいそうなので書きます。

## 症状：連携しても、連携画面に戻ってくる

デモ撮影のため連携し直したところ、こうなりました。

- アプリを開くと、待たずにfreeeの事業所選択画面へ飛ぶ
- 事業所を選んで「許可する」を押すと、また同じ画面に戻る
- **エラーメッセージは一切出ない**

最初は無料プランのスリープを疑いました。Renderの無料プランは15分で停止するので、`/callback` が起動待ちに巻き込まれてコードを失っているのでは、と考えました。

**外れでした。**

---

## 切り分け：どこまでが正常か

推測を重ねる前に、事実を3つ取りました。

### 1. サーバーの応答（Cookieなし）

コマンドラインでトップページを取得すると、**ランディングページのHTMLが正常に返りました。**リダイレクトもしていません。サーバーは無実です。

### 2. `/help` を開く

**正常に表示されました。**問題は `/` だけです。

サーバーが正常で、`/` だけがおかしい。差はCookieです。**セッションがある状態でだけ挙動が変わる。**つまりログイン済みとして扱われ、アプリ本体のHTMLが返っている。

### 3. APIを直接開く

ブラウザで `/api/state` を開きました。

```json
{"error":"freeeへのアクセス権限がありません。","relogin":true}
```

出ました。画面には一度も出ていなかったエラーです。

---

## 原因その1：自動リダイレクトがエラーを隠していた

アプリ本体のJSにこれがありました。

```js
if (d.relogin) { location.href = '/login'; return; }
```

「ログインが切れていたら、連携し直させる」という素直な実装のつもりでした。実際に起きたのはこれです。

```
/ → 画面 → /api/state が失敗
  → 自動で /login → freee認可 →「許可する」→ /callback（成功）
  → / → 画面 → /api/state がまた失敗 → 以下、無限
```

**再認可では解決しない失敗を、再認可で直そうとしていました。**

`location.href` で遷移するので、エラー本文は一瞬たりとも表示されません。利用者にも、開発者にも、何も伝わらない。

自己回復の仕組みは、**回復しない失敗を1つでも含むと無限ループになります。**そして画面遷移で隠れるので、原因に辿り着けません。

まず自動リダイレクトを外し、エラー本文と再連携ボタンを表示するように変えました。

---

## 原因その2：`/api/1/companies` は、連携していない事業所も返す

エラーを表示させたら、こう出ました。

```
freeeとの連携が切れています。再度連携してください。(/api/1/deals)
```

**`/api/1/deals` が401。**しかも `/callback` の中で呼んでいる `/api/1/companies` は**成功しています**（失敗していればエラー画面になっていた）。

同じトークンで、片方は通り、片方は401。

コールバックはこうなっていました。

```python
comps = cl.get("/api/1/companies").get("companies", [])
c0 = comps[0]          # ← 先頭を採っていた
```

freeeの認可画面には、こう書かれています。

> あなた個人の情報の取得や所属事業所情報の取得
> 「八邦システム」**以外の事業所**の事業所名やログイン権限などの情報が含まれます

つまり **`/api/1/companies` は、連携を許可していない事業所も返します。**

私のアカウントには事業所が2つあり、先頭は開発用テスト事業所でした。利用者が別の事業所を選んでも、**先頭のIDを保存してしまう。**

- `/api/1/companies` … 一覧の取得自体は許可されている → **通る**
- `/api/1/deals?company_id=<許可していない事業所>` → **401**

「連携は成功したのに、以降のAPIが全滅する」という、分かりにくい壊れ方でした。

### なぜ今まで動いていたのか

プライベートアプリで開発していた頃は、選ぶ事業所と先頭がたまたま一致していました。**事業所が1つしかない開発環境では、この不具合は絶対に再現しません。**

### 直し方

許可の有無を推測せず、freeeに聞くことにしました。

```python
c0 = None
for c in comps:
    try:
        cl.get(f"/api/1/companies/{c['id']}")   # 参照できるか試す
        c0 = c
        break
    except ApiError:
        continue
```

`prompt=select_company` を指定していても、**どれが選ばれたかはトークンから直接は分かりません。**実際に参照できるかどうかで判定するのが確実でした。

## 推測は外れていた

エラーを隠している間、私はこう考えていました。

> パブリックアプリの「口座明細の参照」は銀行明細取得申請の承認が前提のはずだ。
> 申請は提出済みだが審査中。だから `walletables` が403になっているのだろう。

状況に合っていて、もっともらしい仮説でした。**そして完全に外れていました。**

エラーを表示させた瞬間に確定しました。所要時間は数十秒です。

**推測を重ねる前に、まずエラーを見えるようにする。**分かってはいたことですが、隠していたのが自分の書いたコードだったのが情けないところです。

---

## ところで、403のリダイレクトは必須要件だった

自動リダイレクトを外した直後、審査フォームでこれを読みました。

> 承認されていない権限（スコープ）を必要とするAPIエンドポイントを呼び出した場合、403エラーが返却されるようになりました。
> **403エラーを検知した際の認可画面等へのリダイレクト機能が必須**となりました

外したばかりの機能が、要件でした。

ただ、要求されているのは**403のとき**です。今回のループは**401**で起きていました。分けて考えれば両立します。

- **401（トークン切れ）** … 再認可で直る可能性が高いが、直らないこともある → **遷移せず、理由を表示する**
- **403（権限不足）** … 認可し直せば権限を追加できる → **認可画面へ遷移する**

そのうえで、403側にも歯止めを入れました。

```js
if (d.reauth) {
  const last = +sessionStorage.getItem('reauth_at') || 0;
  if (Date.now() - last > 60000) {          // 60秒に1回まで
    sessionStorage.setItem('reauth_at', Date.now());
    location.href = '/login'; return;
  }
}
// 60秒以内に再発 → 遷移せず、freeeが返した内容をそのまま表示する
```

要件は満たしつつ、**認可しても解決しない場合に無限往復しない。**同じ失敗を繰り返さないための最低限です。

### 403を意図的に起こす

審査には「実装されていること」を示す必要があります。しかし権限は必要なものだけを要求しているので、**普通に使っていると403は起きません。**

確認用の入口を用意しました。

```python
if request.args.get("scope_test") == "1":
    client_for(u).get("/api/1/invoices", {"company_id": u["company_id"]})
```

承認を受けていない `/api/1/invoices` をわざと呼びます。返ってきたのはこれでした。

```json
{"error":"access_denied","message":"このアプリケーションにはアクセス権限がないエンドポイントです"}
```

**freee自身の応答**が画面に出るので、「403を検知している」ことを自分の主張ではなく事実として示せます。

## 提出物：「freee側画面」が存在しないアプリ

審査フォームは、動作確認としてこれを求めます。

> ③ 今回申請する主要な連携機能（データの取得や作成）を実行し、**正しくfreee側で処理されたことがわかるfreee側画面まで**

**本アプリは参照のみで、freeeに一切書き込みません。**該当する画面が存在しません。

黙って出せば「③が不足」で差し戻されます。提出PDFの1ページ目に理由を書きました。

> 更新・作成・削除の権限を一切要求していないため、freee側にデータを作成・変更する処理を行わず、
> 「freee側で処理されたことがわかるfreee側画面」は原理的に存在しません。

**「出せません」ではなく「構造上存在しません、代わりにこれで示します」**と書く。参照専用であることの説明そのものになるので、むしろ有利な材料だと考えました。

なお設問ごとに**最大5ファイル**という制限があります。画面キャプチャは22枚あったので、設問ごとに1本のPDFにまとめ、各ページに「この画面が何を示すか」の注釈を付けました。ファイル名にはアプリ名を入れ、個人名は入れない指定でした。

## まとめ

今日直したのは3つです。

| | |
|---|---|
| **真因** | `/api/1/companies` の先頭を採っていた。**許可していない事業所も返ってくる** |
| **発見を遅らせた原因** | エラー時の自動リダイレクト。**回復しない失敗があると無限ループになる** |
| **未実装だった要件** | 403検知時の認可画面へのリダイレクト。**ループ防止と両立させた** |

いま審査待ちです。フォームには「通常3週間〜4週間」とありました。

このまま気づかず審査されていたら、担当者の画面でも同じ無限ループが起きて、**「起動しないアプリ」として差し戻されていた**と思います。デモを撮るために自分で一通り触ったのが、結果的に唯一の検証機会でした。
